## 2. 数据源扩充（大）：从 6 源到 15+ 源

### 2.1 现状与问题

- `backend/config/source_presets.json` 仅 6 源；需求 3.1 列了 11 个疫情源 + 3.2 人员往来源 + 3.3 基础参考源。
- `jhu_csv` / `owid_csv` 抓取的是 COVID-19 时代数据（JHU 已于 2023 年停更），**长期空转**，占用调度却无新事件产出。
- `web_document` 类型依赖 LLM 解析，无 LLM 配置时不可用——CDC 网页类源缺少"免 LLM"的确定性解析路径。

### 2.2 扩充清单（新增 9 个适配器，按优先级排序）

| 优先级 | 数据源 | 适配器类型 | 内容 | 难度 | 备注 |
|--------|--------|-----------|------|------|------|
| P0 | WHO Global Health Observatory (GHO) | `who_gho_api`（OData JSON） | 各国卫生指标、疾病负担 → `countries.health_capacity` | 中 | 直接替代种子数据，支撑"防控能力"因子 |
| P0 | US CDC Travel Health Notices | `cdc_notices`（HTML 结构化解析） | 旅行健康警告等级（Level 1-3）→ 事件级别映射 | 中 | 免 LLM，BeautifulSoup/lxml 选择器 |
| P0 | WHO Epidemic & Pandemic Intelligence | `rss`（复用现有） | 疫情情报新闻 | 低 | 加预设即可 |
| P1 | WOAH WAHIS | `wahis_api`（REST JSON） | 动物疫情/人畜共患病 → 新 event_type=zoonosis | 中高 | 需注册 token，可先做公开汇总接口 |
| P1 | Global.health | `global_health_api` | 病例线列表 | 中 | 注意数据量，只取聚合 |
| P1 | UNWTO World Tourism Barometer | `unwto_csv` | 各国入境旅游人数 → `countries.travel_intensity` | 中 | 支撑"人员往来强度"因子 |
| P1 | World Bank Open Data | `wb_api`（REST JSON） | 人口、国际旅客到访量（ST.INT.ARVL） | 低 | API 简单稳定，替代静态 population |
| P2 | OpenFlights / OurAirports | `openflights_csv`（静态导入） | 航线网络 → 中转链路图真实化 | 中 | 一次性导入+季度刷新，构建"始发国-中转国-中国"链路 |
| P2 | GHS Index 2019 | `ghs_static`（静态导入） | 国家安全能力评分 → 校准 health_capacity | 低 | 公开 XLSX，一次性导入 |
| P2 | 中国海关总署/外交部公告 | `customs_rss`（有公开 RSS 则接，否则人工录入界面） | 口岸检疫政策、重点国家名单 | — | 内网端已有规则编辑能力可承接 |

### 2.3 落地要点

1. **适配器注册表扩展**（`collectors/service.py: build_adapters` + `schemas.py: SourceCreate.adapter_type` Literal 白名单）——每类一个 Adapter 类，继承现有 `BaseSourceAdapter`，保持 fetch/parse 契约不变。
2. **数据落位双轨**：
   - 疫情事件类 → `disease_events`（现有管道，自动去重评分）；
   - 指标类（GHO/世行/UNWTO/GHS）→ 新增轻量 ETL 作业写 `countries` 表 + `country_risk_history`，不进事件流。
3. **中转链路真实化**：OpenFlights 导入后，`transfer_service.build_payload` 的 `transfer_risks` 从种子数据切换为"航线网络 × 始发国风险"计算结果，地图"中转链路流向图层"随之真实化。
4. **替换停更源**：`jhu_csv`、`owid_csv` 降为 `enabled=false` 保留历史，由 GHO + WOAH 接棒时序数据职责。

**预期收益**：预设源 6 → 15+，六因子中 4 个因子（严重性除外）获得真实持续数据，地图 6 图层全部真实数据驱动。

**工作量**：约 15-20 人日（P0 三项 6 人日即可见效）。

## 3. 采集稳定性（大）：从"能采"到"采得稳、看得见"

### 3.1 现状与风险

- 重试：`BaseSourceAdapter.__init__(retries=3)` 仅是 httpx transport 连接级重试；**429/5xx 无退避重试**，ProMED（15 分钟频率）易被限流封禁。
- 调度：APScheduler 已有 `max_instances=1 / coalesce / misfire_grace_time=300`，基础扎实；但**无失败升级策略**（连续失败不影响调度继续硬撞）。
- 可观测：`source_runs` 表记录了每次结果，但**无健康度聚合、无告警、前端 SourcesPage 无趋势**。
- 数据新鲜度：无"多久没采到新数据"的度量，源静默失效（HTTP 200 但内容不变/空）无法感知。

### 3.2 改进方案（四层防线）

**第一层：网络韧性**
1. 指数退避重试：统一在 `BaseSourceAdapter.fetch` 实现 `429/502/503/504` 退避重试（1s→2s→4s，尊重 `Retry-After` 头），替代裸 retries=3。
2. 超时分级：连接 10s / 读取 60s（大 CSV 源）按源类型配置化。
3. 条件请求：对支持 ETag/Last-Modified 的源（WHO/ECDC RSS）发 `If-None-Match`，304 直接跳过解析，省带宽且防重复解析。
4. 代理支持：`EventSource.config_json` 增加 `proxy_url` 字段，httpx client 按源挂代理（应对境外源网络波动）。

**第二层：调度自愈**
5. 失败熔断：连续失败 N 次（默认 5）自动把该源调度间隔乘以退避系数（×2，上限 24h），成功后恢复原间隔——防止被限流的源持续硬撞。
6. 静默失效检测：每次采集记录 `content_hash`，连续 7 天 hash 不变则标记 `stale` 并告警（源还在但数据死了）。
7. 错峰启动：服务重启时所有 job 加随机 jitter（0-120s），避免 15 个源同秒并发请求。

**第三层：可观测性**
8. 源健康度评分：新增 `GET /api/v1/sources/health`，输出每源近 7 天成功率、最近成功时间、平均耗时、records_created 趋势、健康等级（green/yellow/red）。
9. SourcesPage 升级为"采集监控台"：健康度表格 + 成功率迷你趋势图（recharts 已在依赖中）+ 一键"立即采集"（现有 `/sources/run`）。
10. Dashboard 顶部增加"数据新鲜度"徽章：所有 P0 源最近成功时间最大值，超阈值（如 26h）转橙红。

**第四层：告警触达**
11. 内网端 `ReceiverPage` 增加摆渡链路断链告警（>26h 未收到包）；互联网端采集告警写入 `audit_logs`（level=warning）并可配置 webhook/邮件外发（生产环境）。

**工作量**：约 8-10 人日；第 1/5/8 三项（退避重试、熔断、健康度接口）为核心，4 人日可达 80% 效果。

## 4. 风险评分模型增强

1. **权重可视化配置**（需求 8.2）：`RulesPage` 为 RISK 类规则增加六因子权重滑块（总和恒 100%）+ 保存前"实时预览"——调权重后对当前全量国家试算，红橙黄蓝分布变化对比图，确认后发布新版本（版本机制已有）。
2. **趋势因子真实化**：TREND-v1 规则依赖 `growth_7d`，需 WOAH/GHO 时序数据接入后由 ETL 计算；短期可先用 `country_risk_history` 的评分变化率近似。
3. **模型回归测试**：新增 `tests/test_risk_regression.py`，用固定 fixture 国家数据断言各等级分布稳定，防止调权重引发等级漂移事故。
4. **预警有效期**：`alerts.expires_at` 已有字段但无自动过期任务——维护任务（maintenance）中加"过期预警自动 status=expired"步骤。

**工作量**：约 5 人日。

## 5. 数据摆渡增强

1. **定时自动摆渡**：互联网端调度器增加"每日 02:00 + 每 6 小时增量摆渡"内置作业（复用 `TransferSenderService.create_task`），当前仅靠手动创建任务。
2. **分片断点续传落地**：`transfer.py` 已实现 `chunks()/reassemble()`，但文件通道未使用——`.gpack` >10MB 时写 `GPH_xxx.gpack.1ofN` 分片，内网扫描端先重组再验签；光闸/网闸对单文件大小有硬限制，这是生产必答题。
3. **摆渡数据对账**：内网 `receiver_status` 增加"最近 7 天应收/实收包数、断链天数"统计；互联网端 outbound 目录保留策略（已传 7 天自动清理，防磁盘涨满）。
4. **网闸 SDK 通道**（需求 7.1 第 4 通道）：抽象 `TransferChannel` 接口，文件/MQ/API 三通道实现既有，预留厂商 SDK 插件位，具体对接待目标网闸设备选型后实施。

**工作量**：1/2/3 约 5 人日；4 视设备而定。

## 6. 性能与运维

1. **SQLite 开发库瘦身**：50 万旅客导入后 `intranet.db` 已具规模，建议 `PRAGMA journal_mode=WAL`（已生效）+ 定期 `VACUUM`；为 `passengers(entry_time, risk_level)` 增加复合索引加速默认排序查询。
2. **批量导入接口强化**：`POST /passengers` 对 409 冲突目前整批失败——改为"逐条幂等跳过 + 响应体报告 created/skipped"，配合模拟脚本可天然断点续导。
3. **响应缓存启用**：`ResponseCache` 已实现但开发模式 `REDIS_URL` 为空走直通——生产切 Redis 后对 `/stats`、`/map/geojson` 等重查询加 30s 缓存（配置项已有）。
4. **Prometheus 指标**：`api_request_metrics` 已含 path/method/status/duration，加 `/metrics` 导出（或定时聚合推送网关），接入现有运维监控。
5. **本机 Docker 修复**：当前 Docker Desktop VM 启动失败（`no route to host 192.168.65.7`）阻塞生产化验证——建议 Docker Desktop → Troubleshoot → Reset to factory defaults（虚拟化配置损坏的常规解法），恢复后 `docker compose --env-file .env up -d --build` 一键切换 PostgreSQL/Redis/RabbitMQ 生产栈。
6. **前端分包**：双入口已拆（internet/intranet html），进一步把 `LlmSettingsPanel/RulesPage` 等管理页做 React.lazy 按需加载，首屏只留 Dashboard+Map。

**工作量**：约 6 人日（不含 Docker 环境修复）。

## 7. 安全与合规补强

1. **密码策略**：`UserCreate` 已校验强度，补"90 天过期 + 历史密码不可复用 5 次"（内网端等保测评常查项）。
2. **会话治理**：登出加 refresh_token 黑名单（jti 入 Redis/表）；同一账号并发会话数上限可配。
3. **审计日志防删**：`audit_logs` 已仅审计员可读，再补 API 层禁止任何角色 DELETE（路由层从未暴露删除即可，测试固化）。
4. **信创适配预留**：数据库层已用 SQLAlchemy ORM，迁移达梦/人大金仓仅需换驱动 + 方言微调；前端依赖无外网字体（Noto 系列本地打包），离线校验脚本已有——在部署文档中固化"信创环境 checklist"。
5. **敏感数据分级标注**：`passengers` 表字段标注（证件/姓名/联系方式 = 3 级），导出接口一律走脱敏序列化（现有 `_serialize_passenger` 已达标，测试固化）。

**工作量**：约 4 人日。

## 9. 验收对照（改进后预期）

| 模块 | 原验收标准 | 改进后目标 |
